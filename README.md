# Knievel

> Fearlessly fast ad delivery that steals the show.

Knievel is a self-hosted, multi-tenant direct ad server written in Rust. It
ships one HTTP server, an operator CLI, a browser admin application, PostgreSQL
migrations, a reference Compose stack, and a Helm chart. It is a publisher-side
decision service, not an OpenRTB exchange.

The generated [`openapi.yaml`](openapi.yaml) is the machine contract. The exact
human operation map is [API.md](API.md), and [CODEMAP.md](CODEMAP.md) connects
that surface to its source.

## Status

Knievel is pre-1.0 software. Treat the generated API and current source as the
contract for the revision you deploy; do not infer support from unchecked phase
items or design documents.

| Area | Current fact |

## What ships

### Decision and management API

- `POST /v1/projects/{project_id}/decisions` selects from an in-process
  snapshot using active-window, inventory, blocklist, priority-tier, and
  weighted-choice rules.
- `POST /v1/projects/{project_id}/decisions:explain` returns candidate
  evaluation details without writing a decision event.
- The generated management surface covers org/project reads and provisioning,
  token mint/list/revoke, org ad-library items, project demand and inventory
  resources, creative templates and image upload, and read-only taxonomy. See
  the exact method/path list in [API.md](API.md).
- JSON and query names on the wire are `snake_case`.

The handler still authenticates and opens a project-bound PostgreSQL
transaction before selecting from RAM. Opaque bearer authentication also does
an Argon2-backed DB lookup; JWT verification uses configured JWKS policies.
“RAM hot path” describes selection, not the whole HTTP request.

### Tenancy and auth

- Tenant tables use PostgreSQL `FORCE ROW LEVEL SECURITY`.
- Project handlers bind the principal's `org_id`, prove that the path project
  belongs to that org, and only then bind `project_id`.
- The app role must be non-superuser. Cross-tenant snapshot and rollup work uses
  a separate `NOLOGIN BYPASSRLS` loader role in transaction-local scope.
- Opaque tokens are always available when the DB is configured. Adding one or
  more `auth.jwt.issuers` enables JWT-shaped bearer verification alongside
  opaque tokens; there is no effective `auth.modes` switch.

See [AUTH.md](AUTH.md) for fields, activation rules, and current caveats.

### Events and reporting

Decision, impression, and click events enter a bounded in-process channel. The
current flusher batches in memory but writes each row with its own
`set_config` and `INSERT` inside one transaction; it does **not** use PostgreSQL
`COPY`. A leader-elected job aggregates non-duplicate rows into
`knievel.events_rollup` by settled hour.

`events_raw` is range-partitioned. The partition manager is written to create
daily leaves and detach leaves older than retention. Detached leaves are not
dropped and continue to consume storage until an operator archives or removes
them. The migration's broad 2026 seed leaf overlaps daily bounds during 2026,
so those maintenance passes currently fail before the detach sweep. Capacity
math, event-kind values, and the
current timestamp-sensitive dedup limitation are in
[REPORTING.md](REPORTING.md).

### Admin browser surface

The release image contains the React admin bundle and normally mounts it at
`/admin/`. It supports OIDC Authorization Code + PKCE and a paste-an-opaque-token
fallback. Both paths put bearer material in browser `sessionStorage`; any script
executing in that origin can read it. Serve the admin surface over TLS, control
who can reach it, keep third-party script exposure small, and set
`admin_ui.oidc.require_oidc: true` when paste-token login must be disabled.

`GET /admin/config.json` is deliberately public and contains only OIDC public
client metadata. The API continues to enforce every role check; UI gating is
not authorization. See [SECURITY.md](SECURITY.md).

## Current limitations

These are implementation facts, not roadmap promises:

- Creative image uploads use `InMemoryStore` and return `memory://...` URLs.
  Bytes disappear on process restart and are not shared between replicas. No S3
  or MinIO adapter is wired into the server.
- OpenTelemetry and Sentry fields are parsed, but initialization only logs that
  exporter/SDK wiring is deferred. Structured request logs work; OTel export
  and Sentry delivery do not.
- There is no `/metrics` route. The chart's optional ServiceMonitor points at a
  nonexistent endpoint and is unsupported.
- Each pod cold-loads its snapshot, then polls `config_version` every five
  seconds. LISTEN/NOTIFY is not active, the interval is not configurable, and
  management writes do not bump `config_version`. A write is therefore not
  automatically visible to a running snapshot.
- `api.public_base_url` is parsed but not applied when decision tracking URLs
  are built; current `click_url` and `impression_url` values are relative paths.
- `/readyz` currently checks DB reachability only. In explicitly DB-less mode it
  returns 200 with `ok: no_db_configured`; it does not check snapshot or flusher
  health.
- The raw-event migration's year-wide 2026 seed partition overlaps the daily
  partitions the manager attempts to create in 2026, so the hourly maintenance
  pass errors before retention detachment until that partition layout is
  repaired operationally.
- Some request fields are accepted without their designed behavior. Examples:
  token `expires_at` is not persisted by the mint handler, token IP allowlists
  are stored but not enforced, and `site_external_id` is not resolved by the
  decision snapshot.
- The generated operation set is smaller than older design records. In
  particular, project update/batch upsert, member management, ad-library
  references/batch upsert, and creative PATCH are not shipped routes.

## Verified local quickstart

The demo seeder writes `tmp/knievel-dev-token`, so create that host directory
first. Start only PostgreSQL and the server, wait for migrations, then run the
seeder as the host UID/GID so the token file is writable and owned by you.

```sh
# From the repository root.
mkdir -p tmp

docker compose -f examples/compose/compose.yaml up -d \
  knievel-postgres knievel

until curl -fsS http://localhost:8080/healthz; do sleep 2; done

seed_out="$(docker compose -f examples/compose/compose.yaml run --rm \
  --user "$(id -u):$(id -g)" knievel-seed)"
printf '%s\n' "$seed_out"
```

Capture the IDs printed by `knievel-cli seed-demo` rather than assuming sequence
values:

```sh
PROJECT_ID="$(printf '%s\n' "$seed_out" |
  sed -n 's/^seed-demo: .* project_id=\([^ ]*\)$/\1/p')"
SITE_ID="$(printf '%s\n' "$seed_out" |
  sed -n 's/^  creative_id=.* site_id=\([^ ]*\) zone_id=.*/\1/p')"
AD_TYPE_ID="$(printf '%s\n' "$seed_out" |
  sed -n 's/^  priority_id=.* ad_type_id=\([^ ]*\)$/\1/p')"
TOKEN="$(cat tmp/knievel-dev-token)"

test -n "$PROJECT_ID" && test -n "$SITE_ID" && test -n "$AD_TYPE_ID"
```

The seeder writes directly to PostgreSQL and does not bump `config_version`.
Restart the server to force a cold snapshot load, wait for liveness again, and
issue a real decision with the captured IDs:

```sh
docker compose -f examples/compose/compose.yaml restart knievel
until curl -fsS http://localhost:8080/healthz; do sleep 2; done
sleep 1

DECISION="$(curl -fsS -X POST \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  --data "{\"placements\":[{\"id\":\"header\",\"site_id\":${SITE_ID},\"ad_types\":[${AD_TYPE_ID}]}]}" \
  "http://localhost:8080/v1/projects/${PROJECT_ID}/decisions")"

printf '%s\n' "$DECISION"
printf '%s' "$DECISION" | python3 -c \
  'import json, sys; assert json.load(sys.stdin)["decisions"]["header"]'
```

If the final request races the asynchronous cold load and returns
`snapshot_cold`, wait a second and repeat it. Tear down the disposable stack:

```sh
docker compose -f examples/compose/compose.yaml down -v
```

The Compose-specific notes are in
[`examples/compose/README.md`](examples/compose/README.md).

## Deployment and builds

Release publication starts only from an explicit `v*` Git tag. The current
workflow publishes image tags `X.Y.Z`, `X.Y`, `X`, and `sha-<commit>`, packages
an OCI Helm chart, attaches three signed CLI archives to a GitHub Release, and
regenerates the external Ruby client.

For local image work, the Dockerfile packages prebuilt binaries and admin
assets; it does not compile the repository itself:

```sh
cargo xtask build-image --tag knievel:local
KNIEVEL_IMAGE=knievel:local \
  docker compose -f examples/compose/compose.yaml up -d knievel-postgres knievel
```

Use an immutable `repository@sha256:...` reference for controlled deployments.
See [DEPLOYMENT.md](DEPLOYMENT.md) and the
[chart README](charts/knievel/README.md).

## Test coverage as checked in

Per-PR CI compiles the workspace and benches, runs unit/property, PostgreSQL
integration, API/contract, xtask, OpenAPI drift, frontend, Helm, acceptance,
and generated-gem jobs. Important boundaries:

- DB-backed API/integration tests commonly self-skip without `DATABASE_URL`.
- `tests/acceptance.rs` contains 30 named journeys; seven are active and 23 are
  ignored design skeletons.
- The nine `tests/chaos_*.rs` scenarios are ignored skeletons; the nightly job
  is advisory and currently tolerates their failures.
- The cross-tenant manifest registers all 47 generated project-scoped
  operations, but its `test` names are diagnostic strings. Registration alone
  does not prove every named negative test body exists or ran.
- API documentation is now checked as exact method/path pairs in both
  directions against all 62 generated operations.

See [TESTING.md](TESTING.md) for the planned test architecture, then verify its
claims against the current test files and workflows.
